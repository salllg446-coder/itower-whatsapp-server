# itower-whatsapp-server

خادم Node.js صغير يربط تطبيق itower بواتساب عبر مكتبة Baileys (غير رسمية)،
مصمم خصيصاً للعمل على استضافة **مجانية بدون بطاقة** حتى لو كانت الحاوية
تدخل بوضع "نوم" أو تفقد ملفاتها المحلية عند إعادة التشغيل (مثل SnapDeploy).

## كيف تجاوزنا مشكلة التخزين المؤقت (Ephemeral Storage)

خلافاً للنسخة الأولى، **لا يوجد أي ملف محلي على القرص يحمل بيانات جلسة
واتساب**. كل شيء يُخزَّن في Supabase:

- `whatsapp_sessions.session_creds` — بيانات اعتماد الجلسة الأساسية (creds)
- `whatsapp_auth_keys` — مفاتيح التشفير (pre-keys, sessions, sender-keys...)

هذا يعني: إعادة تشغيل الحاوية (نوم/استيقاظ، نشر جديد، انهيار مفاجئ) **لا
تفقد الجلسة ولا تتطلب مسح QR من جديد** — الخادم يقرأ الجلسة من Supabase
ويستأنف الاتصال تلقائياً عند الإقلاع (`resumeExistingConnectedSessions`).

## آلية منع النوم (Keep-Alive)

الخادم يفتح نقطة HTTP بسيطة `GET /ping` (المنفذ `PING_PORT`, افتراضياً
3000). أضفت workflow جاهز في `.github/workflows/keep-alive.yml` يستدعي
هذه النقطة كل 20 دقيقة عبر GitHub Actions (مجاني بالكامل لمستودع عام).

### خطوات التفعيل:
1. ارفع هذا المجلد كمستودع على GitHub (يمكن أن يكون خاصاً، لكن الدقائق
   المجانية لـ Actions محدودة على المستودعات الخاصة — العام أفضل هنا).
2. انشر الحاوية على SnapDeploy واحصل على رابطها العام (مثل
   `https://xxxx.snapdeploy.app`).
3. في إعدادات المستودع: Settings → Secrets and variables → Actions →
   أضف secret باسم `PING_URL` بقيمة رابط حاويتك (بدون `/ping` في النهاية).
4. الـ workflow يعمل تلقائياً كل 20 دقيقة بعد ذلك.

⚠️ **تنبيهات صادقة يجب معرفتها قبل الاعتماد على هذا الأسلوب:**

- GitHub Actions لا يضمن التوقيت الدقيق لجدولة `cron` — قد يتأخر التنفيذ
  أحياناً 10-15 دقيقة عن الموعد المحدد على المستودعات قليلة النشاط. هذا
  يقلّل هامش الأمان أمام مهلة الخمول (45 دقيقة)، وإن فشل نبضان متتاليان
  فعلياً ستنام الحاوية وتُعاد تشغيلها (لكن بفضل التخزين في Supabase، لن
  تفقد الجلسة — فقط انقطاع مؤقت بضع ثوانٍ حتى يعيد الاتصال).
- هذا النمط (تشغيل خدمة "تنام عند الخمول" بشكل دائم صناعياً) قد يخالف روح
  الاستخدام المقصودة من الطبقة المجانية عند بعض المزودين. لم أجد نصاً
  صريحاً يمنعه من SnapDeploy وقت كتابة هذا، لكن لا ضمانة باستمرار هذا
  السلوك أو عدم تعليق الحساب مستقبلاً دون إشعار.
- مواصفات الحاوية المجانية (512 ميجابايت رام، 0.25 vCPU) قد تكفي لعدد
  قليل من جلسات واتساب المتزامنة فقط — راقب الاستهلاك مع زيادة المستخدمين.

## التشغيل محلياً (للاختبار قبل النشر)

```bash
npm install
cp .env.example .env
# عدّل .env وضع SUPABASE_SERVICE_ROLE_KEY
npm start
# اختبر: curl http://localhost:3000/ping
```

## أمان SUPABASE_SERVICE_ROLE_KEY

هذا المفتاح يتجاوز كل سياسات RLS. ضعه فقط في متغيرات بيئة الحاوية على
SnapDeploy (Environment Variables في إعدادات المشروع) — لا تضعه أبداً في
كود Flutter أو أي مكان يصل إليه المستخدم النهائي، ولا ترفعه لملف `.env`
داخل مستودع Git عام.

## مخاطر معروفة (مذكورة سابقاً، للتذكير)

- Baileys غير رسمية؛ خطر حظر الرقم قائم، خصوصاً مع الإرسال الجماعي لأرقام
  لم تتفاعل من قبل.
- بروتوكول واتساب يتغيّر أحياناً — راقب تحديثات مكتبة Baileys بشكل دوري.
- إعادة الاتصال المتكررة (كل مرة تنام فيها الحاوية وتستيقظ) تعني "قطع
  ووصل" متكرر لجلسة واتساب على مدار اليوم، وهذا نمط اتصال أقل استقراراً
  من جهاز يبقى متصلاً باستمرار بلا انقطاع — قد يرفع احتمال ملاحظة واتساب
  لنشاط غير معتاد على الرقم مقارنة بالاستضافة الدائمة (جهاز منزلي أو VPS).
